# Dev wins — 2026-04-28

## Summary

Today we tightened **compute orchestration efficiency** (the real cost driver right now) without touching the signal-processing core (already efficient: 100 Hz → 20 Hz + 5 Hz LP filter).

---

## Wins shipped

### 1) Preflight validation happens **before enqueue**

**Problem:** bad uploads still paid queue + worker startup cost before failing in the worker.

**Fix:** `POST /api/upload-session` now performs a cheap **preflight session score** after extraction and **rejects early** if the upload is obviously junk (no RQ job created).

- **Code**: `backend/validation/preflight.py`, `backend/routes/upload.py`
- **Checks** (fast):
  - accel/gyro row counts
  - approximate duration (from `time` column)
  - approximate IMU rate (warn-only)
- **Behavior**:
  - On reject: returns **400** and best-effort deletes extracted raw files to avoid retaining rejected data.
  - On accept: enqueues the job as usual and returns optional `warnings`, `duration_s`, `approx_hz`.

**Production knobs (env vars)** live in `backend/config.py`:

- `PREFLIGHT_MIN_DURATION_S`
- `PREFLIGHT_MAX_DURATION_S`
- `PREFLIGHT_MIN_ROWS`
- `PREFLIGHT_MAX_ROWS`

Defaults are permissive for local dev + unit tests; tighten in production.

---

### 2) Worker is now **idempotent + version-aware**

**Problem:** even when a report already existed, the worker would re-run the pipeline by default.

**Fix:** `backend.worker.run_pipeline()` now checks for `processed/report.json` first:

- If it exists and `report["processing_version"] == PROCESSING_VERSION`:
  - **skip** all heavy work
  - mark job **complete**
  - return cached report

Also removed hard-coded `"2.0.0"` usage in the worker in favor of `PROCESSING_VERSION`.

- **Code**: `backend/worker.py`, `transformations/process_session.py` (`PROCESSING_VERSION`)

## What’s next (recommended)

If you want next step, the highest-leverage work now is **system design**, not performance.

### Option A — 1-page data lifecycle spec (enforceable rules)

**Goal:** turn “raw → processed → delete” into a small set of rules that the code can enforce, so storage + compute stay predictable as usage grows.

**Artifacts (current buckets)**
- **Raw**: `RAW_DIR/<session_id>/...` (uploaded/extracted CSVs)
- **Processed**: `PROCESSED_DIR/<session_id>/report.json` (+ processed CSVs / summaries)
- **Plots**: `PLOTS_DIR/<session_id>/*.png`

**Lifecycle states**
1. **INGESTED**: raw exists; no report yet
2. **PROCESSED**: `report.json` exists and matches `PROCESSING_VERSION`
3. **ARCHIVED** (optional): raw deleted; processed + plots retained
4. **DELETED**: everything removed (user delete / retention sweep)

**Enforceable rules (start simple)**
- **R1: Raw retention**: delete raw sessions older than `RAW_RETENTION_DAYS` *only if* a processed report exists (`RAW_DELETE_REQUIRES_PROCESSED=true`).
- **R2: Idempotent processing**: never recompute if `report.json` exists for the current `PROCESSING_VERSION`.
- **R3: Reprocessing policy**: if `PROCESSING_VERSION` changes, do not eagerly reprocess everything. Reprocess **lazily** (on-demand) or by a controlled backfill job.
- **R4: Hard caps**: reject or flag uploads beyond max duration/rows to prevent unbounded worker cost.
- **R5: Deletion semantics**: user-initiated delete removes **raw + processed + plots + DB rows** for that `session_id`.

**Where this lives in code**
- Preflight gates + flag/reject: `backend/validation/preflight.py`, `backend/routes/upload.py`
- Idempotent worker caching: `backend/worker.py`
- Retention sweep mechanism: `scripts/cleanup_raw_sessions.py` (schedule it)

**Deliverable**
- A single page doc: `docs/data-lifecycle.md` that defines the states + rules above, and lists the env vars that control them.

### Option B — Define a “feature store for skiing turns” (minimal + practical)

**Goal:** have a durable, queryable dataset of *per-turn* features for analytics now and ML later, without storing massive raw data forever.

**Proposed shape (v0)**
- **Granularity**: one row per detected turn
- **Primary keys**:
  - `session_id`
  - `run_id` (or `run_index`)
  - `turn_id` (or `turn_index`)
  - `processing_version`
- **Core columns** (already computed today):
  - timing: `duration_s`, `time_s` (or start/apex/finish times)
  - kinematics: `pelvis_turn_angle_deg`, `pelvis_peak_rotation_rate`, `pelvis_max_roll_angle_deg`
  - dynamics: `pelvis_peak_g_force`, `pelvis_turn_radius_m`
  - symmetry/quality: `pelvis_symmetry`, `speed_loss_ratio`
  - context: `speed_at_apex_kmh`, `sensor_source`, `direction`

**Storage locations**
- **SQLite (already)**: `turns` table is effectively the feature store backbone.
- **Optional export**: `PROCESSED_DIR/<session_id>/turn_features.parquet` (or CSV) for easy downstream use.

**Enforceable rules**
- Feature store rows are **versioned** by `processing_version`.
- Feature store is **append/replace per (session_id, processing_version)** to keep it deterministic.
- Raw retention can be short because the feature store is the long-lived product.

**Deliverable**
- A 1-page spec: `docs/feature-store.md` defining the schema + keys + versioning rules, and (optionally) an export format.
